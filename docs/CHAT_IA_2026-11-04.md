# Equipo IA en Taskly web

## Estado

Servidor publicado en **Supabase Edge Functions**, proyecto independiente **Taskly** (`pyzccxqovozizipamrvu`), organización **RonaldArc503's Org**, región `us-east-1`. Firebase conserva los usuarios y los datos en tiempo real. No se activó Blaze ni un plan de pago. El APK no incorpora este módulo.

Dirección base: `https://pyzccxqovozizipamrvu.supabase.co/functions/v1/taskly-agents`. Endpoint MCP: la misma dirección terminada en `/mcp`. Web: `https://tasksv.web.app`.

La creación del proyecto se cotizó a **$0/mes**. El plan Free tiene cuotas compartidas por organización y pausa por inactividad; no es una garantía de capacidad ilimitada. El consumo de DeepSeek se factura aparte por su proveedor. Ver [precios](https://supabase.com/pricing) y [cuotas de invocaciones](https://supabase.com/docs/guides/platform/manage-your-usage/edge-function-invocations).

Usa el conector durante las sesiones de trabajo: sus consultas cada 15 segundos consumen invocaciones y operaciones de Firestore aunque no haya preguntas. Las cuotas de Firebase también se comparten con el resto de Taskly.

El enlace identifica el servidor MCP; la credencial identifica al agente y su proyecto. Compartir únicamente un enlace de la web no conecta una IA ni inicia una conversación automática.

## Flujo en dos PC

1. En **Equipo IA**, crea un proyecto, por ejemplo «Laboratorio de servidores».
2. En **Conexiones**, crea `IA-PC1` y `IA-PC2`. Copia cada credencial una vez y úsala únicamente en su PC. Puedes revocarla o renovarla desde esta pantalla.
3. En **Contexto**, publica un documento por VM o servicio: sistema, configuración relevante, avances comprobados y dudas. También puede publicarlo la IA mediante MCP. No publiques contraseñas ni claves privadas.
4. Copia el bloque **Configuración de OpenCode** y combínalo con el `opencode.json` del proyecto en cada PC. Conserva tu proveedor y modelo DeepSeek; el servicio Taskly no recibe su clave API.
5. Configura `TASKLY_AGENT_TOKEN` en el entorno donde arrancas OpenCode. Cada PC usa una credencial diferente. No añadas la credencial al repositorio ni al enlace.
6. En el chat de trabajo, pide: «Usa Taskly para consultar el contexto, identificar al otro agente y preguntarle qué falta para configurar DNS. Publica los avances comprobados».
7. En la otra PC, pide: «Revisa mi bandeja de Taskly y responde con el contexto publicado». Los cambios se muestran en vivo en la web.

Herramientas MCP disponibles:

| Herramienta | Uso |
| --- | --- |
| `get_project_context` | Lee el resumen, identidades y agentes; con `key` obtiene el documento completo y con `version` una revisión. |
| `publish_project_context` | Publica con `expectedVersion`; un conflicto obliga a leer y combinar cambios. Usa `0` para un documento nuevo. |
| `send_agent_message` | Envía un avance o una pregunta a `targetAgentId`. |
| `read_agent_inbox` | Consulta preguntas pendientes dirigidas a esta conexión. |
| `reply_to_agent_request` | Responde una pregunta concreta; solo admite una respuesta. |

Usa el mismo `requestId` al reintentar la misma operación. El servidor rechaza reutilizarlo con otro contenido. El resumen del contexto tiene un tamaño limitado; consulta por `key` cuando indique que está truncado.

## Respuesta automática opcional

Una conexión MCP permite usar herramientas cuando OpenCode trabaja. Para atender preguntas mientras el chat está inactivo, inicia el conector en la PC que debe responder.

Requiere Node.js 22 o posterior, OpenCode configurado con un modelo disponible y el bloque `taskly-context` generado por Taskly. Este agente utiliza `steps: 1` y `permission: { "*": "deny" }`. El conector verifica esa configuración antes de tomar preguntas.

Terminal 1, en el proyecto que contiene `opencode.json`:

```powershell
opencode serve --hostname 127.0.0.1 --port 4096
```

Terminal 2, tras descargar `taskly-opencode.mjs` desde **Conexiones**:

```powershell
$env:TASKLY_URL = 'https://TU_SERVIDOR'
$env:TASKLY_AGENT_TOKEN = 'CREDENCIAL_DE_ESTA_PC'
node ./taskly-opencode.mjs
```

`TASKLY_URL` es la dirección base del servicio, sin `/mcp`. En este despliegue incluye `/functions/v1/taskly-agents`; copia el valor generado por **Conexiones**. Si proteges OpenCode, establece `OPENCODE_SERVER_PASSWORD` también en la terminal del conector; el usuario predeterminado es `opencode` y puede cambiarse con `OPENCODE_SERVER_USERNAME`.

El conector consulta cada 15 segundos, responde en una sesión dedicada usando el contexto publicado y se detiene tras cinco intentos. `TASKLY_MAX_QUESTIONS` permite elegir de 1 a 100. `--once` realiza una consulta y termina; Ctrl+C detiene el proceso. No lee conversaciones privadas, archivos de las VMs ni el historial del chat de trabajo. Para compartir nuevos avances, publícalos explícitamente en Taskly desde el chat de trabajo o la web.

Cada pregunta admite tres intentos antes de mostrar **Revisar conexión**. El procesamiento tiene una reserva de tres minutos: si se interrumpe el conector, otro intento puede recuperarla al vencer. El propietario puede reintentar desde la web y responder manualmente. La reserva evita que dos conectores publiquen respuestas simultáneas a una pregunta. Renovar o revocar la credencial corta las siguientes solicitudes de la conexión anterior.

## Reproducir localmente

Desde la raíz de Taskly, instala dependencias con Node.js 22 y Firebase CLI disponible. Los emuladores de Firestore necesitan Java compatible con Firebase CLI.

```powershell
npm ci
npm ci --prefix agents-service
firebase emulators:start --config firebase.agents.local.json --project demo-taskly-music --only auth,firestore
```

Otra terminal, servidor local aislado de producción:

```powershell
$env:GCLOUD_PROJECT = 'demo-taskly-music'
$env:FIRESTORE_EMULATOR_HOST = '127.0.0.1:8088'
$env:FIREBASE_AUTH_EMULATOR_HOST = '127.0.0.1:9098'
$env:TASKLY_WEB_ORIGINS = 'http://127.0.0.1:4321'
node agents-service/src/local.mjs
```

Otra terminal, web:

```powershell
$env:PUBLIC_FIREBASE_EMULATORS = '1'
npm run dev -- --host 127.0.0.1 --port 4321 --background
```

Abre `http://127.0.0.1:4321`, registra una cuenta ficticia y crea el proyecto. El proxy local envía `/api/agents` y `/mcp` al puerto 8787. Para detener Astro: `npm run dev -- stop`. Para el servidor y los emuladores: Ctrl+C en sus terminales.

Pruebas con ambos emuladores activos:

```powershell
$env:FIRESTORE_EMULATOR_HOST = '127.0.0.1:8088'
$env:FIREBASE_AUTH_EMULATOR_HOST = '127.0.0.1:9098'
npm run test:agents-service
node --experimental-strip-types --test src/lib/*.test.mjs
npm run check
npm run build
```

Sin las variables de emulador, la prueba de integración se omite; ese resultado no acredita la integración. No emplees las credenciales locales en producción.

## Publicación y mantenimiento

### Supabase elegido para Taskly

La entrada `supabase/functions/taskly-agents/index.mjs` monta el servicio existente bajo `/taskly-agents`. Usa Firestore por REST y el transporte Fetch del SDK MCP para funcionar en Edge sin duplicar la lógica de negocio.

La función tiene `verify_jwt=false` en la puerta de Supabase porque valida sus propias credenciales: Firebase ID tokens para personas y tokens limitados a un proyecto para agentes. Esto no permite acceso anónimo a los datos. Solo `/api/agents/health` es público; los demás endpoints requieren autenticación.

El secreto `TASKLY_FIREBASE_SERVICE_ACCOUNT` está guardado en **Edge Functions → Secrets**. Pertenece a `taskly-agents@tasksv.iam.gserviceaccount.com`, con `roles/datastore.user` y `roles/firebaseauth.viewer`. No está en el código ni en la web. Se puede rotar creando una clave nueva para esa cuenta, sustituyendo el secreto y eliminando la clave anterior después de verificar el servicio. La inicialización del SDK y el formato de la credencial siguen la [documentación de Firebase Admin](https://firebase.google.com/docs/admin/setup).

Para desplegar desde una terminal con Supabase CLI v3 autorizada:

```powershell
npx supabase functions deploy taskly-agents --remote=pyzccxqovozizipamrvu --use-api --no-verify-jwt --yes
firebase deploy --project tasksv --only firestore:rules,firestore:indexes
firebase deploy --project tasksv --only hosting
```

La variable de compilación `PUBLIC_TASKLY_AGENT_SERVICE_URL` está en `.env.production.local` y apunta a la dirección base indicada arriba. Firebase Hosting conserva sus rutas de listas compartidas y ya no apunta a Cloud Functions. No subas credenciales al repositorio ni uses variables `PUBLIC_*` para secretos.

Comprueba `/api/agents/health`, conecta ambas PC, publica contexto y verifica pregunta/respuesta y revocación. Tras crear índices, espera a que `agentRequests` esté **READY** antes de probar la bandeja de preguntas: Firebase puede aceptar el despliegue mientras los está construyendo.

### Servidor HTTPS propio

El servicio también arranca con `node agents-service/src/standalone.mjs` o con el `Dockerfile` incluido. Configura `GCLOUD_PROJECT=tasksv`, `PORT` y `TASKLY_WEB_ORIGINS` con los orígenes exactos de la web separados por comas. Usa credenciales de servidor administradas por el alojamiento mediante ADC, con acceso a Firestore y a la comprobación de usuarios de Firebase Auth. Nunca las añadas a la web ni al repositorio.

Publica el proceso detrás de HTTPS. Antes de compilar la web establece `PUBLIC_TASKLY_AGENT_SERVICE_URL=https://TU_SERVIDOR`. Despliega las reglas e índices. No configures las variables de emulador en el servidor de producción.

## Validación realizada y límites

- Dos clientes MCP reales intercambiaron contexto, pregunta y respuesta mediante Auth y Firestore emulados. Se probaron aislamiento entre proyectos, revocación, respuestas duplicadas, conflictos de contexto, toma simultánea de preguntas, recuperación tras errores y reintentos.
- El conector completo se probó contra un servidor local que reproduce la API HTTP de OpenCode. OpenCode no está instalado en esta PC: falta probar OpenCode con DeepSeek real en las dos máquinas.
- La adaptación pasó seis pruebas en Node y en Deno con transporte REST. En el emulador REST se usó un proxy de pruebas en loopback que restaura su encabezado de administrador; las comprobaciones de permisos de cliente siguieron accediendo directamente al emulador.
- En el servidor público de Supabase, dos clientes MCP reales publicaron/leyeron contexto, enviaron una pregunta, consultaron la bandeja, respondieron y verificaron revocación. La cuenta ficticia y sus datos se eliminaron al terminar. También se verificaron respuestas 200, 401 y 403 y el asesor de seguridad de Supabase no reportó incidencias.
- Desde la web pública se creó un proyecto temporal, se publicó contexto versión 1 y se verificó su aparición automática. Luego se eliminó únicamente ese proyecto y la lista se actualizó sin recargar. La web y las reglas e índices están publicadas; la copia local de la credencial de servidor se retiró después de comprobar el funcionamiento.
- Aprobaron cinco pruebas del servicio en Node.js 22, las 41 pruebas web, 51 comprobaciones de reglas compartidas con Android, análisis estático y compilación web. La interfaz recibió una respuesta MCP en vivo sin recargar; se revisó en navegador de escritorio.
- `npm audit --omit=dev` del servicio no reporta vulnerabilidades tras fijar `rimraf` en `6.1.4`: evita las versiones vulnerables de `glob`/`minimatch` transitivas de los SDK de Google. Mantener el override hasta que las dependencias superiores incluyan una versión corregida; se verificó con Node.js 22.
- El proyecto pertenece a una cuenta humana, que puede usar sus dos PC. Esta primera versión no incorpora invitaciones a otros propietarios ni acceso al escritorio o las VMs. La IA solo conoce el contexto que se publica.
